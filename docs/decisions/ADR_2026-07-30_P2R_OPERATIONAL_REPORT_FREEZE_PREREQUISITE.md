# ADR — P2-R Operational Report and Freeze Prerequisite

- ADR id: `ADR-2026-07-30-P2R-OPERATIONAL-REPORT-FREEZE-PREREQUISITE`
- Tranche: `P2R-OPERATIONAL-REPORT-FREEZE-PREREQUISITE-2026-07-30`
- Phase: `DESIGN`
- Risk: `R2`
- Status: `PROPOSED — SPEC NEXT; BUILD NOT AUTHORIZED`

## Context

Phase 2 cannot truthfully run a complete shift while
`freeze-policy.yaml`'s `report_approved` prerequisite is satisfied only by
an explicit audited override. Migration 002 already contains a `reports`
table, but there is no canonical Report type, lifecycle, repository mapping,
service, API, approval action, deterministic snapshot, or real freeze check.
The existing loose JSON Schema does not match the migration.

P2-R closes that operational gap only. It owns the end-shift operational
record needed to freeze a shift. It does not own Phase 5 templates, narrative
generation, PDF/Excel export, scheduling, analytics, forecasting, or AI
report authorship.

## Decision 1 — one bounded operational report type

This tranche implements one governed report type:

`END_SHIFT`

The application and public contract treat it as a closed enum with that one
value. The database column remains textual so a later governed migration can
add report types without rewriting existing history.

Canonical domain types are:

- `ReportStatus`: `DRAFT`, `IN_REVIEW`, `APPROVED`, `FROZEN`;
- `ReportSourceRef`;
- `ReportSection`;
- `ReportContent`;
- `Report`.

The Report row retains the migration-002 fields:

- `report_id`;
- `shift_id`;
- `report_type`;
- `version`, integer greater than or equal to one;
- `status`;
- `content`;
- `generated_from_cutoff`;
- `created_at`.

P2-R adds `is_current` through a new migration. It is server-owned and marks
the one active version for a `(shift_id, report_type)` pair. Actor authority
is not duplicated into caller-writable Report fields; authenticated actors
remain bound through durable audit and approval-receipt records.

`ReportContent` has this strict shape:

- `schema_version`, fixed to `1.0`;
- `sections`, exactly the server-derived section set below;
- `source_manifest`, one entry per included source record;
- `snapshot_digest`, lowercase SHA-256 hex.

Callers never submit `content`, `sections`, source references, status,
version, cutoff, digest, lifecycle actors, or `is_current`.

## Decision 2 — immutable version history and lifecycle

Each Report row is an immutable snapshot version. Its `content`,
`generated_from_cutoff`, `shift_id`, `report_type`, `version`, and
`created_at` never change. Only these controlled fields may change:

- lifecycle `status`, through a valid forward transition;
- `is_current`, from `true` to `false` only when a successor version is
  inserted in the same transaction.

The normal lifecycle is:

`DRAFT -> IN_REVIEW -> APPROVED -> FROZEN`

Only the current version may transition. `FROZEN` is terminal. A non-current
row remains readable history but can never be reviewed, approved, selected
for freeze, or made current again.

Initial generation creates version 1. Regeneration atomically marks the
previous current row non-current and inserts the next integer version as a
new `DRAFT`. It never overwrites a snapshot.

- A `DRAFT` or `IN_REVIEW` current version may be regenerated by an operator.
- Regenerating an `APPROVED` current version is an approval revocation and
  requires a shift supervisor plus a non-empty reason.
- A `FROZEN` report or a report whose parent shift is `FROZEN` cannot be
  regenerated.

Receipts for an older version stay durable history but cannot authorize a
successor because receipt selection is bound to report id, version, fixed
risk, action, and digest.

Post-freeze correction records remain permitted by the existing freeze
policy. They do not mutate or regenerate the frozen Report. The correction
and its audit are a later addendum to frozen truth; presentation of such
addenda belongs to P5-A.

## Decision 3 — server-derived snapshot and provenance

Generation is allowed only for a governed `CLOSED` shift. The server records
one UTC `generated_from_cutoff` while reading a transactionally consistent
snapshot. The cutoff means "the persisted state observed by this generation
transaction"; it is not a client-supplied timestamp.

The exact sections are:

1. `operational_events`: records for the shift whose evidentiary state is
   `CONFIRMED`, `CORRECTED`, or `FROZEN`;
2. `corrections`: append-only corrections for included operational events;
3. `tasks`: every shift-bound Task, including terminal statuses;
4. `customer_requests`: every CustomerRequest whose `shift_id` equals the
   report shift;
5. `incidents`: every shift-bound Incident, including terminal statuses;
6. `handovers`: every Handover whose `from_shift_id` equals the report shift.

Raw Messages are excluded because they are unconfirmed input. Approval
receipts and audit rows are excluded from report content; they remain
separate governance evidence linked by target identity.

Each section contains canonical JSON snapshots of the corresponding domain
models. Enums are their string values, UUIDs are lowercase strings,
datetimes are UTC ISO-8601, absent values are JSON null, and object keys are
sorted for hashing. Evidence references are sorted by
`(evidence_id, source_type, source_id, sha256)`.

Deterministic record ordering is:

- events by `(starts_at nulls last, event_id)`;
- corrections by `(created_at, correction_id)`;
- tasks by `(created_at, task_id)`;
- customer requests by `(received_at, request_id)`;
- incidents by `(created_at, incident_id)`;
- handovers by `(created_at, handover_id)`.

Each `ReportSourceRef` contains:

- `record_type`;
- `record_id`;
- `source_version`, nullable only for a source model that has no version;
- `source_digest`.

The source digest is SHA-256 over the complete canonical source snapshot.
The overall `snapshot_digest` is SHA-256 over canonical compact UTF-8 JSON
containing `schema_version`, `shift_id`, `report_type`, `sections`, and
`source_manifest`. It excludes report id, report version, status, cutoff,
creation time, and lifecycle actors so equal source truth produces an equal
digest.

Review submission, approval, and freeze recompute the exact snapshot and
require equality of section membership, source digests, and overall digest.
Missing, added, corrected, or otherwise changed source truth makes the
current version stale. Recovery is regeneration, never content mutation.

The SPEC must define a bounded maximum record count and serialized-content
size. Overflow fails closed; truncating a load-bearing operational report is
prohibited.

## Decision 4 — review and approval authority

Add these permission actions:

- `report.generate`: minimum role `operator`;
- `report.submit_review`: minimum role `operator`;
- `report.approve`: minimum role `shift_supervisor`;
- `report.revoke_approval`: minimum role `shift_supervisor`.

The governed chains are:

`report.generate`

`identity -> permission -> closed-shift check -> derive snapshot -> persist version -> audit`

`report.submit_review`

`identity -> permission -> lifecycle -> revalidate snapshot -> persist status -> audit`

`report.approve`

`identity -> permission -> lifecycle -> revalidate snapshot -> R2 approval -> persist status -> audit`

`report.revoke_approval`

`identity -> permission -> reason -> create successor version -> audit`

Report approval uses the existing durable receipt architecture. Add
`("Report", "report.approve")` as an allowed target/action pair. Receipt
creation derives from the stored current Report:

- fixed risk class `R2`;
- exact `report_id`;
- exact `target_version`;
- exact `payload_digest = snapshot_digest`.

Receipt identity, role, and active status are resolved by the existing
authenticated user path. `assert_approval_satisfied` re-resolves current
authority and requires the R2 seat. The actor performing the approval
transition cannot be the sole receipt approver; the existing confirmer
separation rule remains load-bearing.

This tranche does not claim that the draft creator and every reviewer are
distinct people: migration 002 has no creator/reviewer columns and actor
history is held by audit records. It claims only the exact independent
receipt-versus-approving-actor rule above.

Every mutation and its actor-bound audit share one ledger transaction.

## Decision 5 — real freeze binding

The report override is retired. A new freeze request cannot use
`override_unimplemented_prerequisites` or `override_reason` to bypass any
policy prerequisite.

For bounded source compatibility, the two legacy request fields may remain
temporarily accepted only at their defaults (`false` and null). Any attempt
to set the override true or provide a reason is rejected with `422`. They
must be deprecated in OpenAPI and removed only in a later versioned contract.

Inside the same ledger transaction, `ShiftService.freeze` must:

1. re-read and require the shift to be `CLOSED`;
2. run the existing real handover readiness check;
3. select exactly one current `END_SHIFT` Report for that shift;
4. require it to be `APPROVED`;
5. recompute and match its complete snapshot and digest;
6. transition that Report to `FROZEN`;
7. transition the Shift to `FROZEN`;
8. append actor-bound `report.freeze` and `shift.freeze` audits.

Zero or multiple current candidates, a wrong shift/type, non-approved state,
stale snapshot, changed handover, or lifecycle conflict refuses the entire
transaction. Report status, shift status, and both audit rows roll back
together on any failure.

An already-frozen shift is idempotent only when its selected Report is also
`FROZEN` and the stored pairing is unambiguous. A frozen shift paired with
missing, non-current, or non-frozen report truth is an integrity conflict,
not silent success.

Atomicity is claimed only for the tested ledger transaction models. The SPEC
must require transaction isolation/retry behavior sufficient to prevent an
admitted concurrent source mutation from committing between final snapshot
revalidation and freeze. Production load, HA, and managed-database isolation
remain outside the closure claim.

## Decision 6 — migration and backend parity

Migration 002 is not sufficient because it permits duplicate versions and
has no durable current-version selector. Add the next ordered migration to:

- add `reports.is_current boolean not null`;
- backfill deterministically and fail the migration on irreconcilable
  duplicate current history rather than choosing silently;
- enforce unique `(shift_id, report_type, version)`;
- enforce at most one current row per `(shift_id, report_type)` with a
  backend-compatible partial unique index;
- preserve all migration-002 rows and statuses.

SQLAlchemy metadata must match the migration exactly. The canonical model
must enforce version greater than or equal to one and the fixed P2-R report
type before persistence.

Add Report operations to:

- Ledger Protocol;
- InMemoryLedger;
- SqlLedger on SQLite;
- SqlLedger on PostgreSQL.

Required behavior includes create/get/list-current/list-history, lifecycle
update, successor creation, exact duplicate/conflict refusal, deterministic
ordering, deep-copy isolation in memory, reconnect proof, and atomic rollback.
The implementation must use split report-specific repository/table modules
if needed to keep every touched code file within the hard size guard.

Disposable PostgreSQL 16 evidence must use migration-created schema. A
metadata-created SQLite database is parity evidence, not proof that the
PostgreSQL migration ran.

## Decision 7 — HTTP and failure contract

The bounded API is:

- `POST /reports` — generate initial `END_SHIFT` Report from `shift_id`;
- `GET /reports/{report_id}`;
- `GET /reports?shift_id=<uuid>` — deterministic current/history result as
  frozen by SPEC;
- `POST /reports/{report_id}/versions` — regenerate a successor;
- `POST /reports/{report_id}/submit-review`;
- `POST /reports/{report_id}/approve`.

Approval receipts continue through existing `POST /approvals`; approver ids,
roles, receipt ids, target versions, risk, and digests never enter Report
mutation request bodies.

Request models forbid extra fields. Responses expose the canonical row
identity/lifecycle fields and strict ReportContent. They never expose raw
audit internals or accept caller-authored snapshot content.

The SPEC must freeze exact response bodies and these status classes:

- `401`: missing, malformed, expired, or invalid JWT;
- `403`: authenticated principal lacks the required permission or current
  approval authority;
- `404`: shift, report, or receipt target does not exist;
- `409`: wrong lifecycle, non-current target, stale snapshot, missing
  approval quorum, duplicate/ambiguous report, frozen parent, or transaction
  conflict;
- `422`: malformed/extra input, invalid UUID/value, content/record overflow,
  or attempted legacy override.

Every refusal occurs before provider evidence routing and leaves report,
shift, approval, and audit state unchanged except that independently created
approval receipts remain durable facts.

## Decision 8 — contract compatibility and history

The existing `shift-report.schema.json` is a pre-runtime loose draft, not
proof of an implemented API. P2-R evolves it in place without silently
discarding its required public names:

- `report_id`, `shift_id`, `version`, `status`, and `sections` remain;
- `report_type`, cutoff, creation time, current-version flag, source
  manifest, snapshot digest, strict section/source shapes, UUID/date-time
  formats, enums, minimum version, and `additionalProperties: false` are
  added;
- the top-level public `sections`, `source_manifest`, and `snapshot_digest`
  are a deterministic serialization of database `content`, not a second
  mutable copy.

The domain/persistence mapper packs those public content fields into the
single migration `content` JSON value and unpacks them losslessly. Contract
tests must preserve a checked historical fixture of the old loose schema,
prove the intended compatibility fields remain, and mechanically review the
OpenAPI delta.

P2-R may add Report-specific permission actions and freeze behavior only. It
must not change settled incident, handover, authentication, shift-create,
message-admission, or P2-C read semantics except where existing freeze tests
must replace the retired report override with a genuine approved Report.

## Decision 9 — evidence and closure claim

Closure requires:

1. focused domain/lifecycle/service/API/contract tests;
2. full non-live regression;
3. InMemory, SQLite, and disposable PostgreSQL 16 parity;
4. migration first-run/rerun proof and exact container cleanup;
5. duplicate/current-version, stale-snapshot, reconnect, concurrency-boundary,
   audit-failure, and atomic freeze rollback tests;
6. OpenAPI, repository, catalog, session, file-size, secret, diff, and
   workspace-doctor gates;
7. reviewer-owned parent-baseline/revert rehearsal;
8. fresh real-provider governance evidence.

The live evidence path must observe zero provider calls for refusal cases,
including anonymous, unauthorized, stale, missing receipt, ambiguous report,
and override attempts. Exactly one provider call is allowed only after a
real JWT path has generated, reviewed, independently approved, durably
persisted, and atomically frozen the Report and Shift with actor-bound audits.
The production Report API itself does not call a provider.

The maximum closure claim is:

> A closed shift can be frozen only with a current, immutable, server-derived
> `END_SHIFT` Report whose exact version and snapshot digest have a valid R2
> approval; Report freeze, Shift freeze, handover readiness, and actor-bound
> audits are atomic on the proven backends.

It may not claim P5 report rendering/export, AI-generated operational truth,
production provider routing, managed/production PostgreSQL readiness,
assignment/tenant/data-scope authorization, P2-C, P2-D, the full-shift exit
gate, Phase 2 completion, concurrency/load/HA beyond the tested transaction
boundary, or universal report-type support.

## Findings disposition

- `P2R-INTAKE-F1`: resolved by fixed `END_SHIFT`, strict canonical
  row/content/public shapes, and explicit database-content serialization.
- `P2R-INTAKE-F2`: resolved by forward lifecycle, immutable snapshot rows,
  successor versions, current-version semantics, and frozen terminal state.
- `P2R-INTAKE-F3`: resolved by the exact included record sets, canonical
  ordering/encoding, per-source digests, overall digest, and revalidation.
- `P2R-INTAKE-F4`: resolved by JWT permissions plus existing R2 durable
  receipts bound to exact report id/version/digest and confirmer separation.
- `P2R-INTAKE-F5`: resolved by retiring the override and atomically binding
  one current approved Report, handover readiness, Report freeze, Shift
  freeze, and both audits.
- `P2R-INTAKE-F6`: resolved by declaring a new migration unavoidable and
  requiring Protocol/InMemory/SQLite/PostgreSQL parity, history, uniqueness,
  copy isolation, reconnect, conflict, and rollback proof.
- `P2R-INTAKE-F7`: resolved by the bounded API and controlled
  `401/403/404/409/422` matrix.
- `P2R-INTAKE-F8`: resolved by retaining the old public field names,
  explicitly versioning/tightening the pre-runtime contract, preserving
  report history, and protecting settled vertical semantics.
- `P2R-INTAKE-F9`: resolved by focused/full/cross-backend/PostgreSQL evidence,
  exact cleanup, refusal zero-call proof, and one real provider call only
  after the durable admitted path.

## Alternatives rejected

- Keep the audited report override: rejected because the policy prerequisite
  would remain non-load-bearing.
- Let callers submit report content: rejected because omission or fabrication
  could satisfy freeze.
- Overwrite one mutable report row: rejected because approval provenance and
  prior operational truth would be destroyed.
- Select the highest approved version without a current marker: rejected
  because stale approved history could become silently eligible.
- Use migration 002 unchanged and enforce uniqueness only in services:
  rejected because concurrent/direct durable writes could create ambiguity.
- Put actor ids directly in caller-writable report content: rejected because
  authenticated audits and receipts already own that authority.
- Implement PDF/Excel or AI narrative generation in P2-R: rejected because
  those are P5-A concerns and are not prerequisites for a truthful Phase 2
  operational freeze.
