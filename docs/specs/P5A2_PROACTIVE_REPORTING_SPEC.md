Source baseline `fd903371b175e1ea488b6802f20db2b1a33c62d4`; current provenance binding is `721f98dec5472cbc8e70e92fec648b9360d57349`. Risk R2. The accepted INTAKE/DESIGN and full Product Milestone Binding are `docs/decisions/P5A2_PROACTIVE_REPORTING_INTAKE_DESIGN_2026-10-24.md`; this SPEC resolves routine choices without changing its 14-gap coverage.

## Outcome and scope

An authorized operator can inspect scheduled, scoped signals and a one-shift-ahead forecast with source lineage, cutoff, freshness, uncertainty, abstention and history in the application. A human must approve the exact run, version and source digest before any recommendation becomes durable or any operational action is considered. A forecast never constitutes an operational fact. P5-A reporting and operational governed retrieval/RAG readiness gate integrated P5-A2 completion. No source, scheduler, route, UI, provider, model or credential action is authorized by this SPEC.

## R1 — Metric, population, time and limits (`A2-G03`–`G06`)

1. Initial metric `snapshot_incident_count`: integer count of distinct canonical `record_id` values whose `record_type` is `Incident` in the `incidents` section of one `END_SHIFT` report snapshot per distinct eligible shift. Label it “incidents recorded in selected report snapshots per shift,” never actual incidents occurring, an incident rate, or total operational incidence. The population is shifts within the authorized, explicitly complete query scope that have an eligible report snapshot and unambiguous aware times. One shift is one chronological observation; a missing report is missing data, not zero. Forecast horizon is the next eligible shift observation in that same scoped sequence; do not invent a calendar arrival date. Policy version `P5A2-INITIAL-1`; changing metric, cohort, horizon or thresholds needs reviewed versioning, with old results retaining their policy version.
2. `observation_time` is the selected report's `generated_from_cutoff`; `availability_time` is its persisted `created_at`. Both must have explicit UTC offset and normalize to UTC for ordering. `shift_id` breaks tied observation times. A selected report must satisfy `generated_from_cutoff <= created_at <= run_as_of`; reports created after the as-of cutoff are excluded before selection, so their mere presence is not an error. If a selected report's top-level or relevant included source timestamp is naive, missing or contradictory, abstain `TIME_AMBIGUOUS`; included source events later than the selected report cutoff are invalid. SQLite-naive timestamps remain `TIMEZONE_UNSPECIFIED`; never silently attach UTC. Source incident `created_at` is event time as reported in the snapshot; report `created_at` is the observation's availability time. A late report/correction can enter only later origins, never rewrite an earlier fold.
3. A historical origin `t` sees only reports with **both** `created_at <= t` and `generated_from_cutoff <= t`. Select at most one version per shift: highest persisted `(version, created_at, report_id)` available by `t` with valid digest/manifest; conflicting metadata/content for the same `(shift_id, version)`, gaps in required provenance, or a digest mismatch abstain `LINEAGE_INVALID`. Use immutable snapshot bytes and manifest, not today's `is_current` or mutable `status`. A past approval may be asserted only from a timestamped historical approval event provably available by `t`; absent that event, mark approval `UNKNOWN` and do not infer it from today's status. Superseding/correction versions after `t` do not enter the fold. Selection does not require APPROVED/FROZEN status; the UI must label snapshot lifecycle state as observed at run time only, and must not imply historic approval. Duplicate `Incident` record IDs inside one selected snapshot are invalid; never count duplicated versions as extra observations.
4. Input declares an aware UTC-normalized query window `[start, end)` with `start < end <= run_as_of`. A report observation cutoff enters only if in this window; its availability must also be `<= run_as_of`. The input adapter supplies an exhaustive ordered manifest of **eligible shift IDs** for the authorized scope/window and all their report-version candidates, with explicit coverage/retention and `complete=true` attestation. Every expected shift lacking a selectable report returns `SCOPE_INCOMPLETE`, not a zero; a shift outside the manifest cannot be silently introduced. The pure adapter validates this supplied completeness claim but does not prove actual database exhaustiveness or runtime authorization. Candidate shift/report-version counts and per-report incident refs are checked **before** materialization; first-slice caps are 500 candidate shifts, 500 report versions total and 500 incident refs per selected snapshot. Any larger query needs stable server pagination with exhaustiveness proof under a later reviewed contract, or returns `SCOPE_INCOMPLETE`; the first 500 can never mask later candidates. A partial page, unknown retention or changed page boundary is incomplete.
   The adapter returns scope, actor/assignment assertion, query window, `run_as_of`, ordered eligible shift IDs and selected report ID/version/cutoff/created/digest, source manifest IDs/versions/digests, counts and SHA-256 lineage digest. It validates each selected report's **entire immutable content bytes** against its canonical aggregate `snapshot_digest`, then independently validates manifest membership and each canonical record digest; a matching digest string alone is insufficient. Define lineage digest as SHA-256 of canonical UTF-8 JSON (`sort_keys=True`, compact separators, no NaN, UTC timestamps with explicit `Z`) over exactly `{scope_id, query_start, query_end, run_as_of, policy_version, eligible_shift_ids, selected_reports}`; `selected_reports` is sorted by `(generated_from_cutoff, shift_id)` and each item contains `shift_id, report_id, version, generated_from_cutoff, created_at, snapshot_digest, source_manifest` in persisted order with each ref's `record_type, record_id, source_version, source_digest`. Evaluation digest uses the same canonical encoding over `{lineage_digest, policy_version, folds}` with folds in target order and each fold's origin cutoff, target shift/report ID/version/digest/availability, training lineage digest, prediction rational numerator/denominator, comparator rational, target count and exact absolute residual. Historical evaluation independently proves target availability by the outer scoring cutoff. Current active assignment is revalidated at each read, run and approval/use in a later integrated adapter; historical membership alone grants no access. Revocation returns a scoped refusal without leaking source IDs or counts.

## R2 — Deterministic numerical contract (`A2-G08`–`G10`)

5. Sort observations by `(generated_from_cutoff UTC, shift_id)` after as-of selection. A point baseline needs 12 complete eligible observations; an issued forecast additionally needs 12 evaluable later targets, so the effective initial floor is **18** chronological observations (6 initial training observations, 6 assessment targets, 6 calibration targets). The baseline for the next shift is the median of the most recent 6 counts; for an even sample use arithmetic mean of the two middle values. Represent calculations as exact integers/rational values until final presentation; round displayed count forecasts to nearest integer, ties to even, clamp below zero to zero. Reject nonfinite values, counts outside `0..500`, missing intervals, mixed scope/policy or broken chronology. With fewer than 12 observations, abstain `INSUFFICIENT_HISTORY`; with 12–17 or fewer than 12 evaluable folds, abstain `CALIBRATION_UNAVAILABLE`, recording available/required counts. No external model or learned parameter is involved in the initial method.
6. Trend is the difference between median of last 6 and median of preceding 6, shown as signed count per six-shift comparison. An upward/downward signal is emitted only when absolute difference is at least 3 **and** at least 50% of `max(1, preceding median)`; otherwise `NO_TREND`. Anomaly for latest observation is `abs(actual - median(previous 6)) >= max(3, 2 * median absolute deviation(previous 6))`; direction and threshold version are recorded. This first slice emits signals only as part of a `READY` forecast at the 18-observation/evaluation floor; it does not publish a separate signal from 7 or 12 observations. These are review triggers, not statistical significance or operational conclusions. Equality triggers; missing prior values abstain. No denominator such as shifts per day is implied.
7. Backtest exactly the **most recent 12** chronological eligible targets in the complete final sequence, each with at least 6 earlier as-of training observations; first 6 are assessment, last 6 calibration. Do not skip a failed recent fold to select an older favorable one. For each target, origin is immediately before its `observation_time` (one microsecond earlier), with a tied `shift_id` target excluded explicitly; reconstruct all training reports using **both** report `created_at <= origin` and `generated_from_cutoff <= origin`, strictly earlier observation tuple, and exclude the target shift. A target may be scored only when its own selected snapshot exists by outer `run_as_of`; the scoring cutoff is that outer as-of, and its snapshot/version/availability are logged. If late reporting leaves fewer than 6 complete training observations or 12 valid recent targets, abstain `CALIBRATION_UNAVAILABLE`; do not fill gaps from final current versions. No random split, future status/currentness, future correction or target value may enter a training origin. At each origin compare baseline prediction to the subsequently available target, recording origin/target IDs, cutoff, both availability timestamps, exact error and source digests. MAE is exact mean absolute error on the 6 assessment folds; compare to the same-scope persistence comparator (last observed count) on identical folds. Baseline may be displayed as a numerical projection only if its MAE is no worse than persistence; otherwise abstain `MODEL_UNSUPPORTED`. This is a deterministic proposed method, with no claimed accuracy before real historical evaluation.
8. Initial uncertainty band uses the last 6 time-ordered out-of-origin calibration absolute residuals, `q = max(residuals)`; display `[max(0, forecast-q), forecast+q]` rounded outward to integer. Label `in-sample empirical residual envelope, n=6`; never call it calibrated coverage or a 90/95% interval. Report the same-sample inclusion count only as a mechanical check, explicitly `in-sample / not validation`; future prospective coverage needs later independent outcomes. If any residual lacks provenance, abstain. Distinguish numeric point forecast from evidence quality `READY`, `DRIFTED`, `STALE`, `UNAVAILABLE`. No statistical confidence claim is made without later independently accepted calibration evidence and versioned method.
9. Freshness limit is 24 hours after latest selected report `created_at` at run time; older source makes the result `STALE` and prevents new recommendation approval. Drift compares mean absolute error of the 6 calibration folds with the preceding 6 assessment folds; trigger `DRIFTED` when latest exceeds `max(2, 1.5 * prior)` (exact rational comparison). Also trigger on changed cohort definition, coverage/retention, schema/digest policy or a count outside the 0..500 input range. Drifted results remain inspectable with reason and residual lineage but cannot become recommendations; recovery needs a new complete evaluation, a newly versioned accepted threshold if changed, and independent owner review. Absence of 12 evaluable folds is `CALIBRATION_UNAVAILABLE`, never `DRIFT_CLEAR`.

## R3 — Scheduled outcome and ownership contract (`A2-G07`, `G13`)

10. Initial schedule is once daily at 00:00 UTC per explicitly enrolled scope. Identity is `(scope_id, scheduled_utc_date, policy_version)`; exactly one terminal analytical run record is permitted per identity. A late start uses its original scheduled cutoff and records actual start; no data observed after that cutoff enters it. Missed slots produce `MISSED` receipts and are not silently backfilled. A duplicate claim returns the existing run or `IN_PROGRESS`; it cannot start another calculation. Resume after crash uses durable claim/lease plus compare-and-swap terminal write; unknown commit state is `UNKNOWN_RECONCILIATION` and blocks retries/recommendations until the owner reconciles the same identity. A lease expiry alone does not prove no write occurred. Cancellation, revoked assignment, incomplete/stale input, evaluation failure and retrieval unavailability each have explicit terminal reason. No scheduler run writes operational records, dispatches protected actions or creates a durable recommendation automatically.
11. Analytical run terminal grammar and exact field presence are owned by registered family `P5A2-PROACTIVE-OUTCOMES` at `docs/cvf/invariants/p5a2-proactive-outcomes.json`, pinned by `docs/specs/p5a2_proactive_invariant_pin.py` under `docs/cvf/INVARIANT_FAMILY_STANDARD.md`. The independent source is this SPEC. `READY` has forecast, band, lineage digest and evaluation reference. `ABSTAINED` has a closed reason and `source_selected` boolean: lineage digest is required exactly when selection succeeded and forbidden otherwise, with no published numeric forecast or signals. Stale/drifted pure analysis therefore returns `ABSTAINED`; low-level residual diagnostics may remain in bounded test evidence, while future durable inspectable analytical receipts need a separate reviewed adapter. `MISSED`, `CANCELLED`, `DENIED`, `FAILED` and `UNKNOWN_RECONCILIATION` have no forecast or recommendation; unknown reconciliation is not silently retried. Every terminal record has identity, cutoff, policy, source/read attempt state, timestamp and reason where applicable. `source_read_attempts` in this abstract family counts one **logical bounded input-admission attempt**, not database queries, pages, transport or provider calls. Future worker must bind real emitter/API adapters and mutation probes; static pin/guard alone prove only contract structure.

## R4 — Application, context and human decision (`A2-G01`, `G02`, `G11`, `G12`, `G14`)

12. Future authenticated API lists complete scoped runs with bounded cursor pagination, fetches one exact run, and exposes a separate approval transition. It revalidates verified identity, permission and current assignment server side on every request, never trusting client scope/source IDs. Responses include terminal outcome, as-of and actual times, source freshness, horizon/metric/policy/algorithm versions, forecast/band/coverage when present, drift/abstention reason, full authorized lineage view and approval state. A 401/403/404/409/422/503 is explicit, with no cross-scope detail leakage or false success. UI shows busy, history, stale/abstained/unknown, source/citations, thresholds and human approval confirmation; failed or offline writes do not display success. Browser and API tests must exercise real integrated service behavior, not static badges.
13. Numerical output derives from canonical snapshots, never from RAG prose. Integrated explanatory context needs positive evidence that the operational corpus is indexed and current, source/tenant/assignment checks are revalidated, citations resolve to the same authorized lineage, prompt injection is contained, and application route/UI use the governed retrieval/RAG path. Package-only P4-A1/P4-A2 closure is insufficient. Retrieval outage yields `CONTEXT_UNAVAILABLE`; retain numerical analytical evidence if valid, but block integrated completion and recommendation approval. P5-A A7 reporting evidence must also settle before whole milestone acceptance.
14. A durable recommendation requires a distinct human approval receipt bound atomically to `run_id`, immutable run version, scheduled cutoff, policy/algorithm versions, exact lineage digest, freshness/drift state, proposed recommendation digest, verified actor and decision time. On approval, re-read exact run and complete current authorization; compare all bound fields, require `READY`, fresh/clear evaluation, ready context and no prior conflicting decision. Any changed source, correction, supersession, new policy, stale cutoff, revoked actor or changed recommendation invalidates the proposal and requires a new run/approval. Reject duplicate/conflicting approvals deterministically; a denial remains visible. Only the approved recommendation may be stored as actionable. Any later operational mutation is a separate existing governed action with its own permission/approval/audit checks; this SPEC grants no automatic writeback. Analytical receipts may be durable as evidence, separated from recommendation/action state.
15. End-to-end acceptance requires point-in-time lineage and complete-scope proofs on both in-memory and disposable SQL backends, controlled naive-time and >500 refusal/pagination probes, late-report/correction/no-leakage backtests, numeric edge cases, confidence-band/coverage and drift evidence, scheduler duplicate/missed/restart/unknown drills, revoked-auth and stale-context drills, actual API/browser history and exact human approval/rejection, owner review and no silent writes. Any CVF-controls-AI claim additionally requires a separately admitted real-provider request/response receipt under AGENTS.md; mocks prove only non-governance UI structure. Live/key/model/CSV work is presently deferred. Broader backup/restore/security/performance belongs to P5-C and deployment/pilot to P5-D.
